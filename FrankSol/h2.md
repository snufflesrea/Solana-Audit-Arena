# [Week 4][High] `sol_to_franksol` Divides Before Multiplying, Causing Precision Loss and Permanent DoS for Small Deposits

## Finding

**Week**: 4
**Researcher**: @snufflesrea, [@snufflesrea]([http](https://x.com/snufflesrea))
**Severity**: High
**Category**: Arithmetic / Business Logic Error
**Affected function(s)**: `sol_to_franksol`, `stake`


## Description

The `sol_to_franksol` utility function computes how many frankSOL tokens a user receives for a given SOL deposit using the standard proportional formula:

`franksol_out = sol_in * supply / total_sol`

However, the implementation performs the division before the multiplication, inverting the correct order:

```rust
pub fn sol_to_franksol(sol_in: u64, total_sol: u64, supply: u64) -> Result<u64> {
    if supply == 0 || total_sol == 0 {
        return Ok(sol_in);
    }
    let out = (sol_in as u128)
        .checked_div(total_sol as u128)   // ❌ divides first — truncates remainder
        .ok_or(StakeError::MathOverflow)?
        .checked_mul(supply as u128)      // ❌ multiplies after — remainder already lost
        .ok_or(StakeError::MathOverflow)?;
    if out == 0 {
        return Err(StakeError::InvalidAmount.into());
    }
    ...
}
```

Integer division truncates immediately. Any `sol_in` smaller than `total_sol` divides to `0`, and the subsequent multiply cannot recover it — the function then returns `Err(InvalidAmount)` and the entire `stake` transaction is rejected.

Compare with the correct implementation in `franksol_to_sol`, which multiplies first to preserve precision before dividing:

```rust
// ✅ correct order in franksol_to_sol
let out = (franksol_in as u128)
    .checked_mul(total_sol as u128)   // multiply first — no precision lost yet
    .ok_or(StakeError::MathOverflow)?
    .checked_div(supply as u128)      // divide last — truncation is minimal
    .ok_or(StakeError::MathOverflow)?;
```

`sol_to_franksol` should follow the identical pattern with `total_sol` and `supply` swapped.

## Impact

- Any deposit where `sol_in < total_sol` returns `Err(InvalidAmount)` — as the pool grows, the minimum viable deposit grows with it, permanently locking out smaller depositors
- In a mature pool with e.g. 100 SOL deposited, any stake below 100 SOL is completely blocked — the majority of retail users are DoS'd by normal pool growth
- A user staking 1.5 SOL into a 10 SOL pool receives 0 frankSOL and their transaction fails, despite the deposit being economically valid
- Unlike the missing ATA DoS (which has a workaround), this bug has **no user-side mitigation** — the math is wrong inside the program and no amount of transaction construction will fix it
- Severity is **High** — the core staking mechanism is broken for an increasingly large subset of users as TVL grows, and no funds already in the pool are recoverable via normal unstake if the inverse is also affected

## Recommended Fix

Swap the operation order in `sol_to_franksol` to multiply before dividing, mirroring the correct implementation in `franksol_to_sol`:

```rust
pub fn sol_to_franksol(sol_in: u64, total_sol: u64, supply: u64) -> Result<u64> {
    if sol_in == 0 {
        return Err(StakeError::InvalidAmount.into());
    }
    if supply == 0 || total_sol == 0 {
        return Ok(sol_in);
    }
    let out = (sol_in as u128)
        .checked_mul(supply as u128)      // ✅ multiply first — preserve precision
        .ok_or(StakeError::MathOverflow)?
        .checked_div(total_sol as u128)   // ✅ divide last — minimal truncation
        .ok_or(StakeError::MathOverflow)?;
    if out == 0 {
        return Err(StakeError::InvalidAmount.into());
    }
    u64::try_from(out).map_err(|_| StakeError::MathOverflow.into())
}
```

This is a one-line reorder with no API change. The intermediate `u128` arithmetic has sufficient headroom — `sol_in * supply` at maximum u64 values fits within u128 without overflow — so no additional bounds checks are needed.

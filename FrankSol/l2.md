[Week 4][Low] `stake` Event Emits Stale `pool_total_sol` and `franksol_supply` Values

## Finding

**Week**: 4
**Researcher**: @snufflesrea , [@snufflesrea](https://x.com/snufflesrea)
**Severity**:  Low 
**Category**: event error
**Affected function(s)**: [stake]

## Description

After a user successfully stakes SOL, the `stake` handler emits a StakeEvent. However, the event is emitted before the pool accounting fields (`pool.total_sol` and `pool.franksol_supply`) are updated to reflect the new deposit. As a result, the event always reports the pre-deposit state of the pool — the values as they were before the current stake was applied.

```rust

    pub fn handler(ctx: &mut Context<Stake>, amount_sol: u64, min_franksol_out: u64) -> Result<()> {
    let pool = &mut ctx.accounts.pool;
    let user_position = &mut ctx.accounts.user_position;
    require!(amount_sol > 0, StakeError::InvalidAmount);
    if user_position.owner == Address::default() {
        user_position.owner = *ctx.accounts.user.address();
        user_position.franksol_balance = PodU64::from(0);
        user_position.sol_deposited = PodU64::from(0);
        user_position.is_blacklisted = PodBool::from(false);
        user_position.bump = ctx.bumps.user_position;
    } else {
        require_keys_eq!(
            user_position.owner,
            *ctx.accounts.user.address(),
            StakeError::Unauthorized
        );
    }
    require!(!user_position.is_blacklisted.get(), StakeError::UserBlacklisted);

    let franksol_out =
        sol_to_franksol(amount_sol, pool.total_sol.get(), pool.franksol_supply.get())?;
    require!(
        franksol_out >= min_franksol_out,
        StakeError::SlippageExceeded
    );

    Transfer {
        from: ctx.accounts.user.account(),
        to: ctx.accounts.vault.account(),
        lamports: amount_sol,
    }
    .invoke()?;

    let bump_bytes = [pool.mint_auth_bump];
    let mint_seed_bytes: &[&[u8]] = &[MINT_AUTH_SEED, &bump_bytes];
    let signer_seeds: &[&[&[u8]]] = &[mint_seed_bytes];
    let mint_ctx = CpiContext::new(
        ctx.accounts.token_program.address(),
        token_cpi::accounts::MintTo {
            mint: ctx.accounts.franksol_mint.cpi_handle_mut(),
            to: ctx.accounts.user_franksol_ata.cpi_handle_mut(),
            authority: ctx.accounts.mint_authority.cpi_handle(),
        },
    )
    .with_signer(&signer_seeds);
    token_cpi::mint_to(mint_ctx, franksol_out)?;

    emit!(crate::StakeEvent {
        user: *ctx.accounts.user.address(),
        sol_deposited: amount_sol,
        franksol_minted: franksol_out,
        pool_total_sol: pool.total_sol.get(), // old value, havent updated yet
        franksol_supply: pool.franksol_supply.get(), // old value havent updated yet
    });
```
For the very first depositor, both pool_total_sol and franksol_supply will be 0 in the emitted event despite the stake succeeding. For subsequent depositors, the event will always lag by exactly one stake — showing the pool size before their contribution was counted.

Any off-chain indexer, dashboard, or analytics system consuming these events will compute an incorrect pool state and incorrect exchange rate history.

## Impact
- Off-chain data integrity: Indexers, explorers, and dashboards that derive pool state from events will maintain a permanently incorrect view of pool_total_sol and franksol_supply — every event is off by the current deposit
- Exchange rate tracking: The SOL-to-frankSOL ratio logged by the event is incorrect, making historical rate reconstruction from events unreliable
- First depositor edge case: The inaugural stake emits pool_total_sol: 0, franksol_supply: 0, which is maximally misleading — a zero-supply event is indistinguishable from a failed or no-op stake to an event consumer
- No on-chain funds are at risk; the pool state written to the account is correct. Severity is Low — impact is confined to off-chain consumers of the event log

## Recommended Fix
Move the `emit`! call to after both pool fields have been updated, so the event always reflects the post-deposit state:
```rust
// 1. Update pool accounting first
pool.total_sol = PodU64::from(
    pool.total_sol.get()
        .checked_add(amount_sol)
        .ok_or(StakeError::MathOverflow)?
);
pool.franksol_supply = PodU64::from(
    pool.franksol_supply.get()
        .checked_add(franksol_out)
        .ok_or(StakeError::MathOverflow)?
);

// 2. Emit with up-to-date values
emit!(crate::StakeEvent {
    user: *ctx.accounts.user.address(),
    sol_deposited: amount_sol,
    franksol_minted: franksol_out,
    pool_total_sol: pool.total_sol.get(),        // ✅ post-deposit value
    franksol_supply: pool.franksol_supply.get(), // ✅ post-mint value
});
```
This is a one-line reordering with zero runtime cost and no logic change — it purely ensures the event faithfully reflects the state after the instruction completes.

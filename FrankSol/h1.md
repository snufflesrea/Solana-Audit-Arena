[Week 4][Low] `set_yield_direction` Applies New Direction Retroactively, Causing Unfair Reward Accounting

## Finding

**Week**: 4
**Researcher**: @snufflesrea , @snufflesrea(https://x.com/snufflesrea)
**Severity**:  High 
**Category**: error bussiness logic
**Affected function(s)**: [set_yield_direction, withdraw, acrrue_rewards]

## Description

The yield_generator program supports two yield directions — positive (reward) and negative (penalty) — controlled by the authority via `set_yield_direction`. However, rewards are only computed lazily at withdrawal time via `accrue_rewards`, using the current yield direction stored in state at that moment.
This means that when the authority flips the yield direction, the new direction is applied retroactively to the entire staking duration — including time already elapsed under the previous direction. There is no checkpoint or snapshot of accrued rewards taken before the direction change.

```rust
#[derive(Accounts)]
pub struct SetYieldDirection {
    pub authority: Signer,
    #[account(mut, seeds = [STATE_SEED], bump = state.state_bump)]
    pub state: Account<YieldState>,
}

pub fn handler(ctx: &mut Context<SetYieldDirection>, is_positive: bool) -> Result<()> {
    require_keys_eq!(
        *ctx.accounts.authority.address(),
        ctx.accounts.state.authority,
        YieldError::Unauthorized
    );
    ctx.accounts.state.yield_direction_positive = PodBool::from(is_positive);
    Ok(())
}
```
Then at withdrawal, `accrue_rewards` is called with the current direction — with no memory of what the direction was during the staking period:
```Rust
pub fn handler(
    ctx: &mut Context<Withdraw>,
    principal_returned: u64,
    _yield_amount: u64,
) -> Result<()> {
    require!(principal_returned > 0, YieldError::InvalidAmount);

    let now = Clock::get()?.unix_timestamp;
    let state = &mut ctx.accounts.state;
    let position = &mut ctx.accounts.position;
    require_keys_eq!(
        position.owner,
        *ctx.accounts.operator.address(),
        YieldError::Unauthorized
    );
    require!(
        principal_returned == position.principal.get(),
        YieldError::PartialWithdrawNotAllowed
    );

    accrue_rewards(position, state.apy_bps.get(), now)?;

    let reward_for_withdrawal = position.accrued_reward.get();
    let total_out = if state.yield_direction_positive.get() {
        principal_returned
            .checked_add(reward_for_withdrawal)
            .ok_or(YieldError::MathOverflow)?
    } else {
        principal_returned.saturating_sub(reward_for_withdrawal)
    };
```
The two unfair scenarios are:
Scenario A — User loses earned rewards (positive → negative flip)
A user stakes for 15 days under positive yield, accruing legitimate rewards. The authority flips direction to negative. At withdrawal, the user's entire staking duration is penalized — they receive less than their principal despite having staked through a positive period.

Scenario B — User avoids deserved penalty (negative → positive flip)
A user stakes under negative yield direction. The authority flips to positive before the user withdraws. The user receives a reward despite having staked entirely during a negative period.
In both cases, the user's actual historical experience is completely ignored.

## Impact
- Users can lose principal they are entitled to if direction flips from positive to negative after they deposit — a direct and unexpected financial loss with no way for the user to prevent it
- Users can exploit a direction flip from negative to positive by timing their withdrawal to avoid penalties entirely
- The authority (whether malicious or simply misconfigured) can silently harm all existing depositors with a single instruction
There is no event, log, or on-chain signal notifying users that their position value has changed

## Proof of Concept
The following test demonstrates Scenario A: a user stakes for 15 days under positive yield, the direction is flipped to negative, and the withdrawal yields less than the original principal.

## Recommended Fix
Checkpoint accrued rewards for all active positions before the direction change takes effect. Since iterating all positions on-chain is not feasible, the minimal correct fix is to record the timestamp and direction at the time of each direction change, and have accrue_rewards compute piecewise — splitting the staking duration across direction segments.

A practical simpler approach: require users to call an explicit accrue instruction to snapshot their rewards before a direction change, enforced by emitting the change with a time-locked delay (e.g. a pending direction change that activates after N slots), giving users time to checkpoint.
At minimum, set_yield_direction should record both the previous direction and the timestamp of the change in YieldState:
```rust
// In YieldState, add:
pub last_direction_change_ts: PodI64,
pub prev_yield_direction_positive: PodBool,

// In set_yield_direction handler:
pub fn handler(ctx: &mut Context<SetYieldDirection>, is_positive: bool) -> Result<()> {
    require_keys_eq!(
        *ctx.accounts.authority.address(),
        ctx.accounts.state.authority,
        YieldError::Unauthorized
    );
    let now = Clock::get()?.unix_timestamp;
    let state = &mut ctx.accounts.state;

    // Checkpoint before flipping
    state.prev_yield_direction_positive = state.yield_direction_positive;
    state.last_direction_change_ts = PodI64::from(now);
    state.yield_direction_positive = PodBool::from(is_positive);
    Ok(())
}
```
Then accrue_rewards must split the duration at last_direction_change_ts, applying each segment's direction independently before summing.
